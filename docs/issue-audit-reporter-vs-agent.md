## 1. #17：`customCss` 是谁的入口（我方错）

**报告人主张**（2026-09-29 评论）：`customCss` 是 `dsh-better-sidebar@0.21.1` 的配置项，gate 在
`titleBarScheme === "custom"` 上，以 `data-dsh-custom-css` 注入。

**我方当时判断**（2026-09-28）：「DSH 与本插件都没有『通用自定义 CSS』入口……你们本地的 `customCss`
应该是自制的」。

**复核手段**：`npm view dsh-better-sidebar@0.21.1 dist.tarball --registry=https://registry.npmjs.org`
→ 下载 tarball → 解包 `package/lib/client.js`：

| 检查 | 结果 |
|---|---|
| `customCss` 出现次数 | **8**（`lib/client.js`）+ 2（`lib/index.js`） |
| gate 原文 | `scheme === "custom" ? snapshot.prefs.customCss : ""` —— **与报告人引用逐字一致** |
| 注入属性 | `data-dsh-custom-css` 存在 |

**结论**：报告人对，我方错。错因是**检索范围**：当时的 grep 只覆盖「DSH 上游两版本全套包 + 前端 bundle +
本机 profile patch」，没把第三方插件算进去，0 命中就写成了绝对句。已在 2026-09-30 的回复里接受并落进
`AGENTS.md`；本条是「再实测确认」，不是新发现。

## 2. #17 ①：`compatExclude` 的成本（一半对一半错）

**报告人主张**：加一个类名/选择器黑名单配置项。

**我方判断**：①「我们的样式表是构建期编译成字符串一次性注入，用户填的选择器拼不进去，要新开一条运行时
注入通道」；②「必须同时兼容两套设置 API，每加一个配置字段都要在两条通道各写一遍」。

### 实测（Chromium 155 / headless CDP，脚本 `.debug/issue-audit/exclusion-options.mjs`）

**(a) 想用 CSS 白拿「排除」，最省的写法是 `!important + initial`：**

| 元素 | background |
|---|---|
| `.card`（宿主自带底色 `rgb(1,2,3)`） | `rgba(0, 0, 0, 0)` ← **宿主底色被一起抹掉** |
| `.md-code-block`（宿主语义底色 `rgb(27,27,28)`） | `rgba(0, 0, 0, 0)` ← 同上 |
| `CY-8Ka_card`（宿主无底色，A1） | `rgba(0, 0, 0, 0)` ← 这条才是想要的效果 |

⇒ 通用排除**做不到「回到宿主原值」**：它有本事把我们的填充删掉，也有本事把宿主自己的底色删掉
（正是 A2 那类 hazard，只是换了个方向）。

**(b) 想用 `@layer glass` 让宿主规则天然赢：**

| 元素 | background | blur |
|---|---|---|
| `.card`（宿主未分层） | `rgb(1,2,3)` ← 宿主赢，**我们的填充失效** | 仍是 `blur(12px)` |
| `CY-8Ka_card`（宿主无声明） | `rgb(9,9,9)` ← 我们仍然画 | 仍是 `blur(12px)` |

⇒ 分层会让 compat 材质在**所有宿主声明过 `background` 的地方集体失效**，等于皮肤大面积消失；而
「宿主没声明的元素仍被我们画」这一点没变，A1 依旧。

**结论**：①「要新开一条运行时注入通道」**成立**（两个 CSS-only 变体都被实测否掉）。但 ②
「两套 API 各写一遍」**不成立**：`src/settings-catppuccin.ts` 的两套 schema 由**同一张**
`catppuccinSchemaFields()` 生成（`CatppuccinSettingsSchema` 与 `Config` 都是它的产物），加一个字段是一次
编辑。真实成本在别处，而且是**四处**：`stateToMutateOps`（写操作）、`settingsSectionsEqual` /
`sanitizeState`（比较与归一）、Host schema、设置行 UI。当时把成本说错了位置。

## 3. #17 ②：`:where()` 到底能救哪一半（结论对，表述不全）

**报告人主张**：用 `:where()` 降低 compat 规则权重，让宿主/插件原生样式优先，一举覆盖 B、C 与 A1。

**我方判断**：`:where()`「只降权重、不阻止规则生效——模糊和合成层照样挂上，成本不消失，而 C 的问题恰恰
不是 background 被覆盖」。

### 实测（Chromium 155，脚本 `.debug/issue-audit/where-cascade.mjs`）

三族元素 × 两套规则（`[class*="card"]` 与 `:where([class*="card"])`，其余完全相同）：

| 元素（族） | `[class*=card]`（0,1,0） | `:where(...)`（0,0,0） | 判读 |
|---|---|---|---|
| `plain`（宿主声明 `background`） | `rgb(9, 9, 9)` | **`rgb(1, 2, 3)`** | 宿主赢 ⇒ 原生底色恢复 |
| `native`（代码块，A2，宿主语义底色） | `rgb(9, 9, 9)` | **`rgb(27, 27, 28)`** | **A2 被这一招修好了** |
| `bare`（A1 工具行 / A3 孤线，宿主无声明） | `rgb(9, 9, 9)` | `rgb(9, 9, 9)` | 仍然被画 ⇒ A1 没救 |
| `backdrop-filter` | `blur(12px)` | `blur(12px)` | 全都在 ⇒ 合成层成本没变 |
| `outline` | `1px solid` | `1px solid` | 全都在 ⇒ A3 没救 |

**结论**：决策对——我们做的「card 族整体退出、只留 `[data-composer-card]`」把 A1/A2/A3 三类一起消，
而 `:where()` 只消 A2。但当时的表述**漏了一半事实**：它对「宿主自己也声明过的属性」是有效的，正确说法是
「`:where()` 只修 A2 这一类，且不减少 blur 成本」。

## 6. 三条教训（已落进 `AGENTS.md`「与报告人协作」）

1. **评审他人补丁：先重建可运行变体跑测试，再下结论**；读 diff 只用来定位。摘录会丢上下文与缩进，
   本轮两次判断都错在这上面。
2. **给「成本高」的判断前先跑最小实测**。本轮两处成本论：一处被实测支持（通用的 CSS 排除会连宿主
   底色一起抹、`@layer` 会让材质集体失效），一处被自家代码否掉（「两套 API 各写一遍」——同一张字段表）。
3. **检索范围决定结论强度**。写「没有 X」之前先问「我的 grep 覆盖了谁」；`#17` 那句绝对句就是这么来的。
   范围不够时写「在本插件与上游范围内未发现」，不要写成「不存在」。
